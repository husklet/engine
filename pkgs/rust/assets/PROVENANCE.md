# Native engine archives

The crate links one target-specific archive containing both guest backends and
the activation constructor. No native executable is stored or extracted at
runtime. Each is built to `<build-dir>/package/<host os>-<host cpu>/libhl-engine.a`
(`HL_PACKAGE_ARCH_DIR`): `aarch64-apple-darwin` to
`build/package/macos-aarch64/libhl-engine.a` and `aarch64-unknown-linux-gnu` to
`build/package/linux-aarch64/libhl-engine.a`.

Only those two are COMMITTED and published, and only they appear in the generated
block below. The crate also supports `x86_64-unknown-linux-gnu`, whose archive is
a local build product: each archive is ~24 MB against the 10 MB crates.io budget
documented in `../Cargo.toml`, so a third is a publication decision that needs
that budget solved first. `tools/refresh_crate_archives.sh --linux` builds the
NATIVE archive for whichever Linux host CPU it runs on and files it under the
matching triple; `--provenance` certifies only the published pair and refuses to
run on a host that cannot have produced them.

The block below is generated by the CMake `refresh-crate-archives` target and
verified by `check-crate-archives` in CI. Do not edit it by hand.

<!-- BEGIN GENERATED ARCHIVE PROVENANCE -->

```
source-commit: 0d6ca9c090ad257fbbda148004715e2c303d2719
config-abi: 1
source-manifest: d202e39f513b612520e12cc31dab01658bc330fe6e4d2b9065a5482048846605
aarch64-unknown-linux-gnu: b0f9652d5284bd70046e10742f6204aaf9ad363361d332b1e902fbdb6c263b84
aarch64-apple-darwin: 979979e97589739376dd5717af346c2ad6e9149298634070fd817bc3aee03ca7
```

<!-- END GENERATED ARCHIVE PROVENANCE -->

`source-manifest` is a SHA-256 over the SHA-256 of every C source and header the
archives are built from (the CMake archive source export consumed by
`tools/crate_archive_manifest.sh`). It is what makes staleness detectable:
`tools/check_crate_archives.sh` recomputes it and fails when the sources have
moved on from the committed archives. A byte-for-byte rebuild comparison is not
usable here — the build is deterministic for a fixed toolchain, but the compiler
records the absolute checkout directory in every object, so the same commit
built at a different path yields different bytes.

The manifest describes the sources; it does not prove the archive came from
them. That link is the compiled-in build stamp: every object force-includes a
generated header holding `HL-ARCHIVE-SOURCE-MANIFEST:<digest>`, and
`tools/check_crate_archives.sh` requires one distinct stamp per archive, present
in every member, equal to the `source-manifest` above. An archive built from
other sources — a refresh in an incremental build directory that skipped a
changed file, or a hand-committed `.a` — carries the wrong digest, or two
digests, and fails the gate on every lane.

These archives are what `cargo publish` ships; the crate never compiles `src/`.
Whenever `HL_CONFIG_ABI` changes, or any engine change must reach crate users,
regenerate both with a single command:

```
cmake --build build --target refresh-crate-archives
```

On an aarch64 Linux host that builds the linux-gnu archive locally and the darwin
archive on an Apple silicon mac through the `mac` bridge, copies both into
`assets/lib/`, and rewrites the generated block above. Commit the archives and
this file together with the source change. Run it on the aarch64 host: an x86-64
Linux host can run the `--linux` half, but it produces its own triple's archive,
not the published one, and `--provenance` refuses there.

`pkgs/rust/tests/packaged_archive.rs` additionally launches a guest through the
committed archive, so a broken archive fails on both hosts in CI; the manifest
check covers the case it cannot see, where a merely outdated archive still
launches guests fine.

Cargo links the selected archive with whole-archive semantics so the private
pre-main activation constructor is retained in downstream executables. A
macOS application using the engine must be signed with the repository's JIT
entitlements before distribution.

# Alpine test fixture

`alpine/alpine-minirootfs-3.24.1-aarch64.tar.gz` is the unmodified official
Alpine Linux 3.24.1 AArch64 minirootfs, downloaded from:

`https://dl-cdn.alpinelinux.org/alpine/v3.24/releases/aarch64/alpine-minirootfs-3.24.1-aarch64.tar.gz`

Its SHA-256 is
`f55a90f69052c5bd6f92cb09a8f47065970830b194c917a006fb94028e721259`,
matching the adjacent official `.sha256` publication. Package license metadata
is contained in the archive at `lib/apk/db/installed`; corresponding source
packages are published in Alpine's `v3.24/main` repository.
